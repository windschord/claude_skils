# モデルルーティングスキル

会話の内容（作業の種類・難易度・リスク）から、実行するモデルとレビューするモデルを決め、Claude CodeまたはCoworkで実際にそのモデルへ作業を委譲するスキルです。

## 重要な原則

1. **スキルは実行中のセッションのモデルを切り替えられない**: できるのは「サブエージェント／新規セッションをモデル指定で起動する」ことと「ユーザーにモデル切り替えを案内する」こと。切り替えたふりをしない
2. **ユーザーの明示指定が最優先**: モデルの指定があれば、その指定に従う（このスキルの判定で上書きしない）
3. **レビューは作成者より1つ上のモデルへ**: 自己レビューや同格モデルによるレビューで済ませない（対応表は下記）
4. **Haikuは検証できる作業だけ**: 機械的に結果を検証できない作業はHaikuに渡さない。迷ったらSonnet
5. **委譲は完全な指示書つきで**: サブエージェントは会話を知らない。目的・入力・制約・完了条件・出力形式を渡す
6. **実行は推奨ティアで行う**: 推奨モデルが現在のモデルより下位（実装・定型作業）でも、原則として推奨モデルへ委譲する。自分で実行してよいのは、現在のモデルが推奨と同じ場合と、1〜2ステップで終わる軽微な作業だけ（レビュー規則は適用する）

## モデルティアと役割

| ティア | モデル | 担当する作業 |
|--------|--------|-------------|
| T1 | Fable | 高リスク×広範囲な分析・方針判断・プロジェクト計画（Opusでの失敗後を含む）、Opus成果物のレビュー |
| T2 | Opus | 分析（原因分析・影響分析・調査）、レビュー、プロジェクト計画、設計判断、Sonnet成果物のレビュー |
| T3 | Sonnet | 実装、バグ修正、テスト作成、軽度なタスク計画（単一機能の分解）、ドキュメント作成、Haiku成果物のレビュー |
| T4 | Haiku | 定型・機械的な作業（条件を満たす場合のみ。`references/routing_criteria_ja.md`） |

## レビューモデルの対応表

| 作成者のモデル | レビュー担当 | 備考 |
|---------------|-------------|------|
| Haiku | Sonnet | |
| Sonnet | Opus | |
| Opus | Fable | |
| Fable | **別のFable** | 作成時の会話・推論を渡さず、成果物と要求だけを渡した別コンテキストで実行する |

- 作成者が不明な成果物はOpusがレビューする（高リスクならFable）。複数モデルの混在成果物は、最上位モデルの1つ上でレビューする
- **レビューの上限**: 実装・定型作業のレビューは、作成者のモデルにかかわらず、作業種別の基本レビュー（実装はOpus、定型作業はSonnet）で足りる。作成者が現セッションのOpus/Fableでも、実装のFableレビューは不要
- 成果物ができた後、自己評価の確度が90%未満のときは、作成者の1つ上のモデルへレビューまたは助言を求める（実行前の判定には使わない。実行前は要求の曖昧さ・影響範囲・取り消しにくさで判断する）
- Fableが使えない場合（プラン・組織の制限やエラー）は、Opusの別コンテキストでレビューし、上位レビューができなかった旨をユーザーに報告する

## このスキルを使用する場面

- 複数種類の作業（分析・計画・実装・レビュー）を含む依頼で、モデルの使い分けを求められたとき
- 作業の重さに見合うモデルで進めたい、または成果物を上位モデルにレビューさせたいとき
- **使わない場面**: ユーザーがモデルを明示している場合、単発の質問や軽微な修正など、使い分ける意味がない場合

## ワークフロー

```text
[model-routing] ステップ 1/4: 作業の分解と分類
[model-routing] ステップ 2/4: モデル選択（実行・レビュー）
[model-routing] ステップ 3/4: 委譲（環境別アダプタ）
[model-routing] ステップ 4/4: 上位モデルによるレビューと結果統合
```

1. **作業の分解と分類**: 会話から作業を洗い出し、混在していれば（例: 調査→計画→実装）分解して、それぞれをティアに分類する。判定基準は `references/routing_criteria_ja.md`（必要になった時点で読む）
2. **モデル選択**: 作業ごとに実行モデルを決め、成果物ごとにレビューモデルを決める。判定結果は短く表で示す（`assets/templates/routing_note_template_ja.md`）
3. **委譲**: 利用環境を判定し、環境別アダプタの手順で起動する
   - Claude Code: `references/adapter_claude_code_ja.md`
   - Cowork（クラウド／リモートセッション含む）: `references/adapter_cowork_ja.md`
   - 委譲手段がない場合は、推奨モデルをユーザーに伝え、切り替えを依頼する
4. **レビューと統合**: 成果物を1つ上のモデルにレビューさせ、指摘を作成側へ反映する。レビュー手順と差し戻しの扱いは `references/review_escalation_ja.md`

## 進め方の注意

- 判定結果は応答の冒頭か、委譲の直前に1〜3行で示す（例: 「分析はOpus、実装はSonnet、実装のレビューはOpusで行います」）。ユーザーの判断が必要なのは、委譲手段がなくモデル切り替えを依頼する場合だけ
- 1つの応答で完結しない長い作業は、フェーズごとにユーザーへ結果を報告してから次へ進む
- 昇格（Haiku→Sonnet、Sonnet→Opusなど）は、失敗の再現や検証失敗など根拠があるときに行い、理由を記録する
- モデルIDは更新されるため、エイリアス（`sonnet` / `opus` / `haiku` / `fable`）を優先する。IDが必要で分からないときは、推測せずユーザーに確認する
