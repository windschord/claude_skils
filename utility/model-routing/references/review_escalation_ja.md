## レビュー担当の決め方

| 作成者 | レビュー担当 |
|--------|-------------|
| Haiku | Sonnet |
| Sonnet | Opus |
| Opus | Fable |
| Fable | 別のFable |
| 不明 | Opus（高リスクならFable） |
| 複数モデルの混在 | 最上位モデルの1つ上 |

**上限**: 実装・定型作業のレビューは作業種別の基本レビュー（実装はOpus、定型作業はSonnet）で足りる。現セッションのOpus/Fableが実装した成果物でも、Fableレビューは不要。

**Fableが使えない場合**: Opusの別コンテキストでレビューし、上位レビューができなかった旨をユーザーに報告する。

作成者は「その成果物を実際に生成したモデル」。現在のセッションのモデルが直接作った成果物も、そのモデルを作成者とする。

## Fableの成果物のレビュー

Fableには上位モデルがないため、**別のFable（別コンテキスト）**でレビューする。

- 作成時の会話・推論過程・結論の理由づけは渡さない。成果物と、元の要求・制約だけを渡す
- 作成者のFableが出した結論を前提にせず、結論を独立に導けるかを確認させる
- 判断が割れたときは、両論と根拠をユーザーに示し、ユーザーが決める

## レビュー依頼の渡し方

レビュー担当は会話を知らない。次を渡す。

| 項目 | 内容 |
|------|------|
| 目的 | 成果物が満たすべき要求（元の依頼文・受入条件） |
| 対象 | 成果物そのもの（差分・ファイル・文書） |
| 観点 | 正確性、要求との整合、抜け漏れ、リスク、保守性（作業種別に応じて絞る） |
| 制約 | 変更してよい範囲、触ってはいけないもの |
| 出力形式 | 指摘ごとに「重要度・場所・理由・修正案」。指摘なしの場合も確認した観点を書く |
| 禁止 | レビュー担当が成果物を直接書き換えること（修正は作成側が行う。ユーザーが許可した場合を除く） |

コードのレビューでは、リポジトリのレビュースキル（`self-review` / `ai-code-review`）の観点・テンプレートを併用してよい。

## 指摘の扱いと差し戻し

1. 重要度の高い指摘から作成側へ反映する。作成側が同意できない指摘は、理由を添えてレビュー担当へ再確認する
2. 差し戻しは最大2回まで。解消しない場合は、論点を整理してユーザーに判断を求める
3. 同種の指摘が繰り返された作業種別は、作成側を1段上げて再実行する（昇格）。理由を記録する。昇格後のレビューは新しい作成者の1つ上（上限規則の範囲内）
4. レビュー結果は「担当モデル・観点・指摘件数・対応状況」を短く報告する

## レビューを省略してよい場合

- 誤字修正、コメントの追記、フォーマット調整のように、意味が変わらない変更
- Haikuの機械的な作業で、機械検証（件数一致・スキーマ検証・テスト）が通っている場合（検証結果の確認で代える）

省略した場合は、省略した旨と理由を報告に含める。
