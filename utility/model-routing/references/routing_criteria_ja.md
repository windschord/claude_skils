## 判定の手順

1. 会話から「ユーザーが最終的に求める成果物」と「そのために必要な作業」を列挙する。要求が曖昧、または解釈が複数ある場合は、Opusによる要求整理の工程を前置する
2. 作業ごとに下表の種別へ分類する
3. 難易度・リスクの昇格／降格条件を当てはめる
4. 成果物ごとにレビューモデルを決める（作成者の1つ上）

## 作業種別とティア

| 作業種別 | 基本ティア | 例 |
|---------|-----------|-----|
| 分析（原因・影響・トレードオフ・調査） | T2 Opus | 障害の根本原因分析、変更の影響範囲、技術選定の比較 |
| レビュー（コード・設計・計画・文書） | 作成者の1つ上 | PRレビュー、設計レビュー、計画の抜け漏れ確認 |
| プロジェクト計画（複数フェーズ・複数担当・依存関係あり） | T2 Opus | ロードマップ、マイルストーン分解、リスク洗い出し |
| 設計判断（アーキテクチャ・データモデル・API境界） | T2 Opus | 方式の選定、境界の引き方 |
| 実装（コード作成・修正・テスト） | T3 Sonnet | 機能追加、バグ修正、リファクタリング、テスト追加 |
| 軽度なタスク計画（単一機能の分解、手順化） | T3 Sonnet | 1機能のタスク分割、チェックリスト作成 |
| ドキュメント作成（仕様が確定済み） | T3 Sonnet | README更新、テンプレート埋め |
| 定型・機械的な作業 | T4 Haiku（条件あり） | 一覧収集、形式変換、機械的な置換 |

## 難易度・リスクによる昇格と降格

### 昇格（1段上げる）

- 影響範囲が広い（複数モジュール、公開API、データ移行、セキュリティ、課金）
- 取り消しにくい（本番反映、削除、外部送信）
- 同種の作業で同じ失敗が繰り返された

> 成果物ができた後の確度（90%未満）による助言依頼は、実行モデルの昇格ではなく「レビュー」の規則（`review_escalation_ja.md`）で扱う。

### 降格（1段下げる）

- 仕様・入力・出力形式が確定しており、判断の余地がほぼない
- 既存の実装パターンをなぞるだけで、結果をテストや差分で機械的に検証できる

降格先がHaikuの場合は、「Haikuを使う条件」をすべて満たすこと。満たさなければSonnetのままにする。実装（コード生成・修正）は原則としてSonnetより下げない。

### 上限・下限

- 実装をOpusへ上げるのは、昇格条件に該当し、その理由を判定メモに記録した場合に限る。実装をFableへは上げない（難所は分析をOpus/Fableで先に行い、実装はSonnetに渡す）
- 分析・レビュー・プロジェクト計画を自動でSonnet以下に下げない（降格条件は実装や定型作業にのみ適用する）
- Fableは「Opusでは足りない」と判断できる根拠（高リスク×広範囲、Opusで失敗した、Opus成果物のレビュー）があるときに使う。昇格条件に該当しても、Opusの実行とFableのレビューで足りる場合は、その運用を優先する

## Haikuを使う条件

次の**すべて**を満たす場合のみHaikuに任せる。1つでも欠ければSonnetにする。

| 条件 | 判断の目安 |
|------|-----------|
| 入出力が固定 | 入力の形と出力の形式を指示書だけで完全に指定できる |
| 判断が不要 | 解釈・取捨選択・設計判断を含まない |
| 機械的に検証できる | 件数の一致、スキーマ検証、テスト、差分確認などで正誤を確認できる |
| 副作用が小さい／元に戻せる | 破壊的な変更や外部送信を含まない（含む場合は別途承認） |
| 規模が小さい | 1回の作業が少数のファイル・件数で収まる |

Haikuに向く例: ファイル／シンボル一覧の収集、grep結果の機械的な集計、JSON⇄YAMLなどの形式変換、決まった様式への転記、一括リネームの案作成、ログからの特定パターン抽出。

Haikuに向かない例: 非自明なコード生成・修正、複数ファイルにまたがる整合性が必要な作業、要約や評価のように判断を含む作業、仕様が未確定の作業。

### Haikuの安定運用

- 結果は必ず検証する（検証方法は指示書に含める）。検証に失敗したら、Haikuで再試行せず**1回目の失敗でSonnetへ昇格**する
- Haikuの成果物はSonnetがレビューする（レビュー対応表どおり）。レビュー対象が機械検証済みの定型出力であれば、検証結果の確認をもってレビューとしてよい
- 同一セッション内でHaikuからSonnetへの昇格が2回発生した作業種別は、以降そのセッションではSonnetに割り当てる

## 混在した会話の分解例

| 会話の内容 | 分解 | 実行モデル | レビューモデル |
|-----------|------|-----------|---------------|
| 「この障害の原因を調べて直して」 | 原因分析（`sdd-troubleshooting`）→ ユーザー承認 → 修正実装 | Opus → Sonnet | 分析はFable／実装はOpus |
| 「新機能のタスクを切って実装して」 | 軽度な計画 → 実装 | Sonnet → Sonnet | Opus |
| 「移行プロジェクト全体の計画を立てて」 | プロジェクト計画（昇格条件に該当するが、Opus実行＋Fableレビューで担保） | Opus | Fable |
| 「全ファイルのヘッダーをこの形式に揃えて」 | 一覧収集 → 変換（小バッチに分け、バッチごとに差分とスキーマで機械検証。バッチが大きい・検証できない場合はSonnet） | Haiku（または Sonnet） | Sonnet（検証結果の確認） |
| 「このPRをレビューして」 | レビュー | PR作成者のモデルの1つ上（不明ならOpus） | — |
