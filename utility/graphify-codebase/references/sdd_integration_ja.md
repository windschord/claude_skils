# SDDフェーズ別 Graphify 活用ガイド

SDDの各スキルから Graphify を呼び出す際の共通ルールと、フェーズ別の手順。全フェーズ共通で「**任意・仮説・実コードで確認**」の原則を守る（詳細は `../SKILL.md`）。

## 共通ルール

1. 調査の最初に `command -v graphify` と `graphify-out/graph.json` の有無を確認する。無ければ**黙ってフォールバック**し、導入を強要しない（導入提案は最初の1回だけ）
2. 照会の前に毎回 `graphify update .` を実行する（Gitの状態からグラフの古さは判定できないため）
3. 照会結果は**候補リスト**として扱い、採用前に必ず Read で実コードを確認する
4. 成果物（設計ノート・レビュー指摘・Issue本文）には、Graphify由来の情報であること、`EXTRACTED` / `INFERRED` の別、実コードで確認済みかどうかを区別して書く
5. 1フェーズ1応答の原則に従い、Graphifyの調査だけで長時間応答を止めない（1回の調査は数コマンドに留める）

## 1. 設計（PR本文の設計ノート）

設計は永続化せず PR本文・GitHubコメントに書く運用（`sdd/requirement-management/references/design_in_pr_ja.md`）。Graphifyは「設計ノートの根拠となる既存構造の把握」にのみ使う。

| やりたいこと | コマンド |
|-------------|---------|
| 既存の主要コンポーネントを把握 | `graphify god-nodes --top 10` → `graphify explain "<ハブ>"` |
| 対象要求に関連する既存コードを探す | `graphify query "<要求の主題>"` |
| 変更が波及する範囲を洗い出す | `graphify affected "<変更するシンボル>" --depth 2` |
| 新規部品と既存部品の接続点を探す | `graphify path "<既存A>" "<既存B>"` |

手順:

1. 対象要求（REQ-ID）の要求文からキーワードを抽出する
2. `query` / `explain` で関連コードの候補を出し、Read で確認する
3. `affected` で影響範囲を出し、`assets/templates/impact_analysis_note_template_ja.md` に整理する
4. PR設計ノートの「実装上のトレードオフ」付近に「影響範囲」として貼る

要求間の影響分析は従来どおり `reqctl.py impact` を使う（Graphifyは要求ではなくコードの依存関係を扱う）。

## 2. タスク計画

Issue本文の「変更対象ファイル」の根拠を補強する。

1. タスクの主題ごとに `graphify query` を実行して候補ファイルを出す
2. Readで確認できたものだけを Issue本文の変更対象ファイルに記載する
3. 確認できていない候補は「要確認」と明記する（サブエージェントが推測で進めないようにするため）

## 3. 実装（task-executing）

| タイミング | 手順 |
|-----------|------|
| 着手前 | `graphify query` / `explain` で触るファイルを絞り、Read は絞った範囲に限定する |
| 実装中 | 変更対象シンボルに対して `affected` を実行し、テストすべき範囲を確認する |
| 完了後 | `graphify update .` でグラフを更新する（次タスクで古いグラフを参照しないため） |

並列実行（Agent tool + worktree）では、**各worktreeで独立にグラフを更新する**。`graphify-out/` を worktree 間で共有しない。

## 4. レビュー（逆順レビュー・ai-code-review・self-review）

差分の「見えている範囲」だけでなく、**差分の外にある影響先**を確認するために使う。

1. 差分から変更されたシンボル（関数・クラス・設定キー）を抽出する
2. 各シンボルに `graphify affected "<シンボル>"` を実行する
3. 差分に含まれていない呼び出し元・依存先が見つかった場合、それらが変更の影響を受けないか Read で確認する
4. 実際に問題がある場合のみ指摘にする。`INFERRED` エッジだけに基づく指摘は「確認事項」として区別する

レビュー指摘に Graphify由来の根拠を書く場合の書式:

```text
**影響範囲（Graphify: EXTRACTED、実コード確認済み）**: `OrderService.cancel()` は `RefundJob`（src/jobs/refund.ts:42）からも呼ばれるが、本PRでは未修正。
```

## 5. トラブルシューティング

原因の特定は従来どおり `sdd-troubleshooting` の手順（推測禁止・実コードの追跡）に従う。Graphifyは追跡の補助のみ。

| やりたいこと | コマンド |
|-------------|---------|
| エラー発生箇所からエントリポイントまでの経路 | `graphify path "<エントリポイント>" "<エラー箇所>"` |
| 修正の波及範囲 | `graphify affected "<修正対象>"` |
| 原因候補の周辺構造 | `graphify explain "<原因候補>"` |

経路は**原因の候補を出すためのもの**で、原因の特定は実コードのトレースとログで行う。修正方針の承認ゲートでは、影響範囲として `affected` の結果（確認済みのもの）を添付する。

## 6. 要求管理（requirement-management）

`reqctl.py` は要求・ストーリー・関係を扱い、コードの依存関係は扱わない。現時点で Graphify との自動連携は行わない。要求変更の影響分析では、`reqctl.py impact` の結果に加えて、必要に応じて変更提案レポートへ影響範囲調査ノートを添付する程度に留める。

## 導入判断のめやす

| リポジトリの性質 | 推奨 |
|-----------------|------|
| コード中心（数百ファイル以上、依存が複雑） | 導入の効果が大きい。`graphify update .` から始める（`calls` / `imports` の関係が取れる） |
| ドキュメント・設定中心（このスキル集のように Markdown が主体） | `graphify update .` で見出しの構造と文書間のリンク参照までは、APIキーなしで取り込める（本リポジトリで約3,750の見出しノード、文書間の参照39件）。ただしエッジの大半は見出しの親子関係で、概念間の意味的な関係は入らない。Grep で足りる調査が多く、効果は限定的。意味的解析まで行うと、外部送信とコストを伴う |
| 小規模（数十ファイル） | Grep/Read で十分なことが多い。導入しない選択も妥当 |
| 機密性が高い | `graphify update .`（ローカル完結）までにする。意味的解析（`--code-only` なしの `extract`）は承認なしに実行しない |

効果の確認は `graphify benchmark` で行える。ただし出力される倍率（本リポジトリでは 94.1 倍）は、Graphify が用意した汎用の質問での値で、実際の調査での削減量とは限らない。実際の調査で、`query` / `affected` の結果が Grep より速く正しい候補に届くかを見て判断する。

## 実行確認の記録（graphify 0.9.92、本リポジトリ）

| 確認した操作 | 結果 |
|-------------|------|
| `update .`（`extract` なし、APIキーなし） | 成功。約3,890ノード。3つの出力ファイルを生成 |
| `extract . --code-only` | 成功。136ノード。`graph.json` のみ |
| `cluster-only . --no-label` | 成功。`GRAPH_REPORT.md` と `graph.html` を生成 |
| `god-nodes` / `explain` / `affected` | 期待どおり。`explain` は各接続に `EXTRACTED` を表示 |
| `query` | 動作。ただし予算（2000トークン）を超えて約6900トークンを出力 |
| `path`（同一ファイル内の関数同士） | `contains` 経由の自明な経路になる |
| 終了コード | `4`（該当なし）と `3`（複数ファイルで曖昧）を再現。近い一致では `0` のまま警告が出る |
| 新規ファイルの追加後の `update .` | 新しい関数がノードとして追加された |
