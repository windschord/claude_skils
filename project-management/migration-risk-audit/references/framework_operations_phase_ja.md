# 運用設計フェーズ特化フレームワーク

運用設計フェーズでは、「システムは動いているが、業務が回らない」あるいは「トラブル時に誰も動けない」という事態を防ぐことが目的。マルチベンダー環境における「運用業務の境界線」を明確にするための4視点。

## 1. 障害時の責任分界点と一次切り分け

- エンドユーザーや店舗から「エラーが出た」と申告があった際の、最初の検知（監視ツール）と、一次切り分け（どのベンダーのシステム起因か）を誰が行うかのフロー
- ベンダー間で原因が特定できない「グレーゾーン」の障害が発生した際の、合同調査（War Room等）の招集ルール

## 2. 日常運用（定常業務）のプロセスと権限

- マスタデータの更新（メニュー変更、キャンペーン設定等）や、ユーザーからの問い合わせに伴うデータ修正を、「誰が・どの画面で・誰の承認を得て」行うか
- 各ベンダーが提供する管理画面へのアクセス権限（ロール）の設計と、退職者発生時の権限剥奪プロセス

## 3. 計画停止（メンテナンス）とパッチ適用

- 特定のベンダー（SaaSやクラウド基盤など）が定期メンテナンスで停止する場合の、システム全体への影響範囲と、ユーザーへの事前告知フロー
- 緊急のセキュリティパッチ適用やマイナーバージョンアップを行う際の、他システムとの結合テスト省略基準および承認プロセス

## 4. 事業継続計画（BCP）とバックアップ復旧

- 致命的なデータ破損やランサムウェア被害が発生した場合の、各システム間でのバックアップ取得タイミングの整合性（RPO/RTOの合意）
- バックアップからデータを復元した際、他システムへ連携済みのデータとの間に生じる不整合（ズレ）の解消手順

## 入力データの調整

このフレームワークで分析する際は、「運用フロー図案」「体制図」「非機能要件定義書」などを分析対象データとして優先的に収集する。運用設計書そのものを新規に作成する場合は operations-design / ipa-nfr-operations-design スキルへ誘導する。

## 分析時の狙いどころ

各視点について、「本プロジェクトで極めて漏れやすく、かつ重大な影響を及ぼす潜在リスク」を2つずつ特定する。特に以下を優先する:

- 障害切り分けフローや管理画面の権限設計が「まだ決まっていない」または「口頭合意のみ」の領域
- 定例メンテナンスや緊急パッチが他ベンダーのシステムに波及することが明文化されていない箇所
- RPO/RTOがベンダーごとにバラバラで、復旧後の不整合解消手順が定義されていない箇所
