# 負荷試験フェーズ特化フレームワーク

負荷試験の計画段階・実施直前のプロジェクトでは、「単一システムの性能テストでは見えにくい死角」が最大のリスクになる。「ベンダー間の連鎖障害」「本番特有のデータ状態」「限界突破時の挙動」を洗い出すための4視点。

## 1. シナリオの現実性と突発的スパイク

- 徐々に負荷をかけるテストだけでなく、特定時刻にアクセスが殺到する「スパイクアクセス（例：予約開始直後の0時00分）」のシナリオ有無
- 「参照（Read）」だけでなく、DBロックやトランザクションが集中する「更新・書き込み（Write：決済、在庫引き当て等）」の負荷比率の妥当性

## 2. マルチベンダー連携と境界ボトルネック

- 自社システムは耐えられても、後続の連携先（外部決済API、旧システム側DB、SaaS基盤）の「レートリミット（API制限）」に引っかかり全体がダウンするリスク
- システム間のコネクションプーリング枯渇や、タイムアウト設定の不整合（Aシステムは30秒待つが、Bシステムは10秒で切断するなど）によるエラー連鎖

## 3. 本番同等の「データ状態」とキャッシュ

- 本番相当のデータボリューム（数百万件のレコード等）が入った状態での検証か（データが空の環境でのテストはSQLのインデックス漏れを検知できないため）
- 本番切り替え直後を想定した、「CDNやDBのキャッシュが完全に空（コールド状態）」からの急激な負荷シナリオの有無
- データの生成・更新・参照・期限切れ・アーカイブ・削除という一連のライフサイクル全段階が、負荷試験項目として過不足なく網羅されているか（例：大量データの一括削除、保持期限切れバッチ、アーカイブ処理がピーク負荷と重なるケースがテスト項目から漏れていないか）

## 4. 限界突破時の挙動と「縮退運転」

- 想定以上の負荷がかかった際、システムが「どのように死ぬか」（無応答になるか、503エラーを返すか、Waiting Room/順番待ち画面に誘導できるか）の検証
- 高負荷状態でシステムがダウンした後、負荷が下がった際に「自動的に復旧（自己治癒）するか」、手動での再起動が必要かの確認

## 入力データの調整

このフレームワークで分析する際は、「負荷試験計画書」「テストシナリオ」「構成図」「WBS」などを分析対象データとして優先的に収集する。想定されるピークイベント（クリスマス予約開始、TVCM放映、プッシュ通知の一斉配信等）も必ずプロジェクト前提条件として確認する。

## 出力時の表現調整

このフレームワークで`assets/templates/risk_audit_report_template_ja.md`のリスク表を埋める際は、負荷試験・本番障害という文脈に合わせて見出しを次のように読み替える:

- 「なぜ危険か（放置した場合の最悪のシナリオ）」→「なぜ危険か（本番で発生した場合の最悪のシナリオ）」
- 「起票すべき具体的なタスク名」→「起票すべき具体的な検証タスク・確認事項」

## 分析時の狙いどころ

各視点について、「本プロジェクトで極めて漏れやすく、本番障害に直結する潜在リスク」を2つずつ特定する。特に以下を優先する:

- 負荷試験計画・シナリオに明記されていない、スパイクアクセスや書き込み系の負荷パターン
- 自社システムの限界値のみを検証し、連携先ベンダーのレートリミットやタイムアウト設定との整合が確認されていない箇所
- 空データ・ウォームキャッシュの環境でしか検証されておらず、本番相当のデータ量・コールドキャッシュでの挙動が未検証な箇所
- 限界突破後の挙動（縮退運転・自動復旧）が、仕様書・試験項目のどちらにも定義されていない箇所
- 負荷試験計画のテスト項目一覧を「データのライフサイクル（生成→更新→参照→期限切れ→アーカイブ→削除）」の軸で棚卸しし、特定の段階（特に削除・アーカイブ・期限切れバッチ処理）が負荷条件下でのテスト項目として漏れていないか
