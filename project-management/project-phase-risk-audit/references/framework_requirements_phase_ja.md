# 要件定義フェーズ特化フレームワーク

要件定義フェーズでは、「既存仕様のブラックボックス化」と「非機能要件の漏れ」が最大のリスクになる。「どう作るか」の前に「何を移して、何を捨てるか」を確定させるための4視点。

## 1. 現行仕様のブラックボックスと非互換性

- 現行システムで「誰がどう実装したか分からない」暗黙の仕様や、ハードコードされたロジックの洗い出し方針
- 新システム（パッケージやSaaS等）の標準機能と、現行システムの要件が合わない場合の「Fit&Gap」における「業務側への運用回避（運用でカバー）」の合意形成

## 2. 非機能要件とパフォーマンス制限

- マルチベンダー環境下における、各システム間のAPIコール数（スロットリング）、データ転送量、処理遅延の許容値
- 旧システムと同等、あるいはそれ以上のトラフィック（ピーク時）に耐えられるかどうかの定量的な基準設定

## 3. データ移行要件（クレンジングとマッピング）

- 現行システムに存在する「ゴミデータ（テストデータ、不整合データ）」を新システムへ移行する前のクレンジング方針
- 旧システムと新システムでデータ型や文字コード（外字・特殊文字など）が異なる場合のマッピングと変換ルール

## 4. セキュリティと監査要件

- 複数ベンダーが開発に携わる際の、本番データ（個人情報など）をマスキングしてテスト環境へ移行する要件
- 新システム稼働後、監査ログ（誰がいつデータにアクセスし、変更したか）をどのシステムで統合管理するかの要件

## 入力データの調整

このフレームワークで分析する際は、「現行システムの課題一覧」「要求仕様書案」などを分析対象データとして優先的に収集する。要求そのものの定義・矛盾検証が主目的の場合は requirement-management スキルへ誘導する。

## 分析時の狙いどころ

各視点について、「本プロジェクトで極めて漏れやすく、かつ重大な影響を及ぼす潜在リスク」を2つずつ特定する。特に以下を優先する:

- 「たぶん今まで通りでよい」と暗黙に扱われている現行仕様
- Fit&Gap分析の対象になっていない、業務側の運用回避が必要になりそうな機能差分
- クレンジング・マッピング・マスキングなど、データ移行の準備作業として明示的にタスク化されていない項目
