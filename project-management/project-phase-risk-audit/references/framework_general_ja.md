# 汎用フレームワーク（移行実行フェーズ向け）

総合テスト終盤・移行リハーサル前など、実行フェーズに差し掛かったプロジェクトの死角を洗い出すための4視点。正常系の設計や特定ベンダーの担当範囲内に隠れがちな「ベンダー間の隙間」「業務影響」「異常系」を狙う。

## 1. データのライフサイクルと異常系

- 移行直前〜停止期間中に発生する「未確定・処理中データ（トランザクション）」の扱い
- データ移行が「一部だけエラーになった場合」の特定方法と手動復旧フロー
- 新旧システム並行時のデータ同期、または旧システムデータの参照・アーカイブ手段

## 2. すべての周辺アクター（IT以外のステークホルダー）

- 現場スタッフ・店舗・営業担当（新システムへの習熟、切り替え当日の業務代替手段）
- コールセンター / CS（切り替え時の問い合わせ急増対応、トラブルシューティング権限）
- 後続・周辺システム（会計、BI、外部API等のバッチ連携の互換性とタイミング）

## 3. 時間軸の境界（本番以外の時間帯）

- 移行前の「コードフリーズ（開発凍結）」と「コンテンツ/マスタ変更凍結」のルール
- システム停止期間中に空振りする「定期バッチ処理（日次集計、有効期限切れ処理等）」の扱い
- 切り替え完了後の旧システムの「サンセット（安全な解約・データ破棄）」プロセス

## 4. マルチベンダーの責任分界点（ポテンヒット）

- 複数システムが絡む障害発生時の「一次切り分け」と「エスカレーション」のルール
- 本番切り替え時の「Go/No-Go判定」の定量的な基準と、最終意思決定者の不在リスク
- 「作る側（開発）」と「受け入れる側（運用・ビジネス）」の間の検証タスクの漏れ

## 分析時の狙いどころ

各視点について、「本プロジェクトで極めて漏れやすく、かつ重大な影響を及ぼす潜在リスク」を2つずつ特定する。特に以下を優先する:

- 提供された分析対象データ（Backlog/課題/WBS）に記載が無い、または記載が薄い項目
- 正常系の設計書やタスク一覧の「行間」にある、誰の担当か曖昧なタスク
- 単一ベンダーの視点では気づきにくい、ベンダーをまたぐ受け渡しのタイミングや条件
