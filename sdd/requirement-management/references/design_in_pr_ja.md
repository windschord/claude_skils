# 設計をPRに閉じる運用

## なぜ設計書を持たないのか

設計書は、書いた瞬間から実装とずれ始める。ずれた設計書は「読むと嘘をつく資料」になり、整合性チェックの対象がひとつ増えるだけで、誰も得をしない。

一方で**要求と理由は陳腐化しにくい**。「なぜそれが必要か」は実装方式が変わっても残る。そこでこの運用では、

- **永続化する**: 要求・理由・要求間の関係（＝変わりにくいもの）
- **永続化しない**: 設計（＝変わりやすく、コードが正になるもの）

設計そのものは実装時に必ず行う。ただし記録先はPR本文とGitHubコメントに限り、レジストリにはPRのURLだけを `design_refs` として残す。

## 実装時の流れ

```text
1. generated/traceability.md から実装対象の要求IDを選ぶ
2. 設計を検討する（データ構造、API、処理フロー、代替案の比較）
3. PR本文に設計ノートを書く（assets/templates/pr_design_note_template_ja.md）
4. テストを書く。テスト名に要求IDを含める（例: test_REQ_0002_login_latency）
5. 実装する
6. 要求の verification にテスト参照を登録する
7. validate --check-tests を実行する
8. design_refs にPRのURLを追加する（URLのみ）
```

## PRに書くこと・書かないこと

| PR本文に書く | レジストリに書く |
|-------------|-----------------|
| 採用したデータ構造・API形状 | なし |
| 処理フロー、シーケンス | なし |
| 検討した代替案と却下理由 | なし（要求の理由に影響した場合のみ `alternatives_rejected`） |
| 実装上のトレードオフ | なし |
| 対象要求ID | 実装対象の要求IDは要求側の `verification` で表現 |
| PRのURL | `design_refs` に追加 |

## 設計中に要求の問題が見つかった場合

実装してみて初めて「要求が矛盾している」「要求が実現不能」と分かることがある。その場合は**実装で辻褄を合わせない**。

```text
1. 実装を止める
2. 何が矛盾・不能なのかを具体的に書く（どの要求とどの要求か）
3. impact <ID> で影響範囲を出す
4. 変更提案レポートを作り、★ ユーザー承認 ★ を得る
5. 要求を直してから実装を再開する
```

要求に書かれていない挙動を実装したくなった場合も同じ。まず要求を追加する。

## テスト条件の定義

このスキルでは、テストの合格条件を次のとおり定める。

1. `validate --strict --check-tests` がエラー・警告ゼロで終了すること
2. `generated/traceability.md` の全ストーリー行に検証手段が埋まっていること
3. 各要求の `verification` に指定したテストが実際に通ること

つまり「設計どおりに作れたか」ではなく、**「要求を満たしたか」「ユーザーストーリーが達成されたか」**だけがテストの合格条件となる。

## PRレビューでの確認事項

- [ ] 変更した要求IDがPR本文に列挙されている
- [ ] 設計ノートに代替案と却下理由が書かれている
- [ ] 新規・変更要求に対応するテストがある
- [ ] `validate --strict --check-tests` がCIで通っている
- [ ] `generated/` が再生成済みで、手編集されていない
- [ ] 設計内容がレジストリのYAMLに漏れ出していない（`rationale` に実現方式が書かれていないか）
