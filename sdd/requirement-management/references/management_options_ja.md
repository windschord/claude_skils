# 管理方式の比較検討と採用理由

単純なMarkdownドキュメントで要求を管理すると、整合性・矛盾のチェックが人手に依存し、件数が増えるほど破綻する。そこで4案を比較し、案1を採用した。

## 評価軸

| 軸 | 内容 |
|----|------|
| 機械検査 | 矛盾・欠落をツールで自動検出できるか |
| 人間の把握 | 全体像を人が短時間で掴めるか |
| 履歴 | 「なぜ変えたか」が残るか |
| 導入コスト | 仕組みを作る手間、既存運用との摩擦 |
| 破綻しにくさ | 要求が100件を超えても回るか |

## 案1: YAMLレジストリ＋検証スクリプト（採用）

要求を構造化YAMLで持ち、Pythonスクリプトが構造・参照・矛盾を検査する。人が読む一覧・トレーサビリティ表・関係グラフは生成物として自動出力する。

- **正**: `docs/requirements/*.yaml`
- **検査**: `reqctl.py validate`（CIで強制）
- **閲覧**: `generated/index.md` / `traceability.md` / `graph.md`

**利点**: 数値矛盾・事実矛盾・孤立・循環・検証欠落を機械判定できる。ローカルで完結し、CIで差し止められる。人間向けの表は生成物なので手入力のずれが起きない。

**欠点**: YAMLを書く学習コストがある。議論の経緯はGit履歴とPRに分散する。

## 案2: GitHub Issue台帳

1要求＝1 Issue。ラベル（`req:active` / `req:superseded`）で状態を、Issueリンクで依存関係を表す。既存のSDDタスク運用（`sdd:task`）と同じ思想。

**利点**: 議論・決定の経緯がIssueに自然に蓄積する。既存運用と一貫する。通知やアサインなどGitHubの機能に乗れる。

**欠点**: 全体を一括検査しにくい（API越しの全件取得を伴うためCIが重い）。数値矛盾の自動判定にはIssue本文の構造化が必要で、結局YAMLに近いものを本文に埋め込むことになる。全体俯瞰も一覧画面頼りとなり、100件を超えると人手で把握できない。

## 案3: Gherkin実行可能仕様

要求を `features/*.feature` としてGherkin（Given/When/Then）で書き、そのままテストとして実行する。

**利点**: 要求とテストが完全に一致する。「要求を満たしたことがテスト条件」という方針に最も直結する。

**欠点**: 非機能要求（性能・セキュリティ・制約）を表現しにくい。要求どうしの依存・置換・矛盾という**要求間の関係**を表す語彙がない。用語ゆれや数値矛盾は検出できない。テストランナーへの依存が発生する。

## 案4: ハイブリッド（YAML＋Issue同期）

YAMLを正としつつ、各要求をIssueへ双方向同期する。

**利点**: 機械検査と議論履歴の両取り。

**欠点**: 同期機構の実装・保守コストが最大。同期ずれ自体が新しい不整合源になる。

## 採用理由

今回の要件は「要求のみを管理」「理由を必ず紐付ける」「追加・変更・削除のたびに整合性と無矛盾性が保たれる」である。**無矛盾性の常時保証**が最優先要件であり、これを人手のレビューに委ねる案は要件を満たさない。

案1は、矛盾判定に必要な最小限の情報（`measures` の数値制約と `asserts` / `forbids` の事実主張）だけを構造化し、残りは自然言語のまま扱うことで、機械検査と記述しやすさを両立する。人間の把握しにくさというYAMLの弱点は、一覧・トレーサビリティ表・Mermaidグラフの自動生成で補う。

## 将来の移行余地

- 案2へ寄せたくなった場合: `validate --json` の出力を使ってIssueを生成できる。YAMLが正のまま、Issueを閲覧・議論用のビューとして追加すればよい（＝案4への段階的移行）。
- 案3へ寄せたくなった場合: `verification` の `kind: test` を feature ファイルのシナリオ名に向ければ、Gherkinをテスト層として併用できる。要求間の関係管理はYAML側に残す。
