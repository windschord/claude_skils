## 終了コード

| コード | 意味 |
|--------|------|
| 0 | 問題なし（`--strict` 指定時は警告もゼロ） |
| 1 | エラーあり。マージしてはならない |
| 2 | `--strict` 指定時に警告あり |
| 3 | PyYAML 未インストール |

## エラー（ERROR）

エラーが1件でもあれば、その変更をコミット・マージしてはならない。

対処は下表のとおり機械的に決まる（レジストリの記述ミスの修正であり、原因分析を要する不具合ではない）。ただし、検査結果が**実装側の欠陥**を示している場合は別で、直接直さずに `sdd-troubleshooting` で事象確認と根本原因分析を行い、ユーザー承認を得てから修正する。該当するのは次のような場合。

- `E-TESTMISS` が、テストの消失や実装の退行によって出ている
- 要求どうしの矛盾（`E-CONFLICT-*`）が、実装済みの挙動と食い違っており、どちらが正しいか自明でない
- 検査は通るのに実装が要求を満たしていないことが分かった

| コード | 内容 | 対処 |
|--------|------|------|
| `E-LOAD` | YAMLパース失敗、ID重複、トップレベル型不正 | 構文を直す。ID重複は片方を採番し直す |
| `E-SCHEMA` | 必須フィールド欠落、enum値・日付書式の不正 | `references/data_model_ja.md` の表と突き合わせる |
| `E-IDFMT` | IDが `REQ-0001` / `US-001` 形式でない | `next-id` で採番し直す |
| `E-REF` | `depends_on` などの参照先が存在しない | IDの誤記か、参照先の削除。参照先を復活させるか参照を外す |
| `E-CYCLE` | `depends_on` / `refines` が循環している | 依存の向きを見直す。相互依存は多くの場合1つの要求に統合できる |
| `E-RATIONALE` | `rationale` がない、`why` が10文字未満 | 「なぜこの要求が必要か」を書く。書けないなら要求自体を疑う |
| `E-SUPERSEDE` | `supersedes` の関係と `status` が食い違う | 置換された側を `superseded` にする。誰にも置換されていない要求を `superseded` にしない |
| `E-RETIRE` | 廃止済みなのに `rationale.retired_why` がない | 廃止理由を書く。墓標は理由が本体 |
| `E-DEAD-REF` | 生きている要求が廃止済み要求を参照している | 置換後の要求へ付け替える。付け替え先がないなら参照元も廃止を検討 |
| `E-DEAD-STORY` | ストーリーに紐付く要求がすべて廃止済み | ストーリーを `done` / `dropped` にするか、後継要求を紐付ける |
| `E-DUPLINK` | ストーリー側に `acceptance` が書かれている | 削除し、要求側の `stories` で紐付ける |
| `E-CONFLICT-ONEWAY` | `conflicts_with` が片方向 | 相手側にも宣言する。宣言は両者の合意である |
| `E-CONFLICT-NOTRADEOFF` | 衝突を宣言したのに `rationale.tradeoff` がない | なぜその衝突を受け入れるのかを書く |
| `E-CONFLICT-NUM` | 同一 `subject` の数値制約が同時に成立しない | 数値を直す／`subject` を分ける／衝突を宣言する |
| `E-CONFLICT-FACT` | 同一 `key` への主張が食い違う、または assert と forbid が衝突 | 値を揃える／`multi_value_keys` に登録する／衝突を宣言する |
| `E-NOVERIFY` | `active` な要求に `verification` がない | テスト・計測・手動確認のいずれかを定義する |
| `E-ORPHAN-US` | ストーリーに有効な要求が1件も紐付いていない | 要求側に `stories: [<ID>]` を追加する |
| `E-TESTMISS` | `--check-tests` 時、テストファイルが存在しない | パスを直すか、テストを実装する |

## 警告（WARN）

放置してよいものではないが、コミットは妨げない。リリース前に棚卸しする。

| コード | 内容 | 対処 |
|--------|------|------|
| `W-RATIONALE-SRC` | `rationale.source` が未記入 | 出所を書く。半年後に「誰が言ったか」が失われる |
| `W-RATIONALE-DATE` | `rationale.decided_at` が未記入 | 決定日を書く。鮮度検査が効くようになる |
| `W-STALE` | 決定から `stale_days` 超過 | 理由がまだ有効か再確認し、`decided_at` を更新するか要求を見直す |
| `W-AMBIGUOUS` | 曖昧語を含む | 測定可能な条件に置き換える。置き換えられないなら `measures` を付ける |
| `W-EARS` | EARS記法に沿っていない | 「〜の時、システムは〜しなければならない」の形にする |
| `W-TERM-ALIAS` | 用語ゆれ | 用語集の正規語に統一する |
| `W-TERM-UNDEF` | 用語集にない語を `terms` に書いた | 用語集に定義を追加する |
| `W-DUP` | 要求文が90%以上類似 | 統合するか、違いが分かる文言に直す |
| `W-ORPHAN-REQ` | 機能要求がどのストーリーにも紐付いていない | 紐付けるか、`type` を `constraint` に見直す |
| `W-UNIT` | 同一 `subject` で単位が混在 | 単位を統一する。統一するまで数値矛盾は検出されない |

## 矛盾検出のしくみ

### 数値制約（`E-CONFLICT-NUM`）

同一 `subject` の制約を区間として扱い、積集合を取る。

```text
REQ-0002: auth.login.latency <= 2s   →  (-∞, 2]
REQ-0005: auth.login.latency >= 5s   →  [5, +∞)
積集合 = 空 → 矛盾
```

1. ペア単位で判定し、「どの2件が衝突しているか」を報告する。区間制約の充足不能は必ず「下限 > 上限」を作る2件が存在するため、ペア判定で網羅できる
2. `!=` は、他の制約で値が1点に確定した場合のみ衝突とみなす
3. `conflicts_with` を相互宣言した**ペア**は判定から除外される（許容済み）。除外はペア単位であり要求単位ではないため、許容済みの要求が**別の相手**と起こす矛盾は通常どおり検出される
4. `!=` の判定では、値を確定させている要求（下限側・上限側）を特定し、`!=` 側がそのすべてと衝突を宣言済みの場合にのみ報告を省く
5. 単位が混在する `subject` は誤検出を避けるため判定をスキップし `W-UNIT` を出す

`status` が `draft` / `active` の要求だけが判定対象。廃止済みは対象外。

### 事実の主張（`E-CONFLICT-FACT`）

同一 `key` に対する `asserts` の値が食い違う、または `asserts` と `forbids` が同じ `key=value` を主張すると矛盾。`policy.multi_value_keys` に登録した key は値の食い違いを許す。

## 機械検査で捕まえられないもの

以下は検査を通っても矛盾している可能性がある。要求の追加・変更時にClaudeが**必ず目視で確認**する。

| 種類 | 例 | 見つけ方 |
|------|-----|---------|
| 意味的な重複 | 「30分無操作でログアウト」と「セッションは最大24時間」が別subjectで両立しているが、実質的に前者が支配的 | 同じドメインの要求を並べて読む |
| 暗黙の前提の衝突 | 「オフラインで動作」と「操作のたびにサーバ検証」 | ストーリー単位で通しで読む |
| 粒度の不一致 | 巨大な要求1件と、それを細分化した要求群が併存 | `refines` を使って階層化する |
| 理由の陳腐化 | 参照している外部規約が改定済み | `W-STALE` を起点に `rationale.source` を辿る |
| ストーリーと要求の意味的乖離 | 紐付いてはいるが、要求を全部満たしてもストーリーが達成されない | `generated/traceability.md` を通読する |

これらを見つけた場合は、`change_workflow_ja.md` の変更フロー（承認ゲート付き）に乗せる。
